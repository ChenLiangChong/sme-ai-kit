# 30 — 派工 prompt 模板（照抄填空，別即興）

> 讀者：主 session（派工者）。`{…}` 是填空。每份模板都內建派工三件套（目標與動機 / 驗收條件 / 回報格式）與範圍圍欄。
> 派給誰、用什麼 model：查 `10-model-dispatch.md` §2。共通鐵則寫在模板外就不重複：subagent 沒有你的對話脈絡，**所有它需要知道的事都要寫進 prompt**。

## T1 搜尋 / 定位（Explore，sonnet）

```
目標：找出 {要找的東西：符號 / 行為 / 慣例} 的所有位置。
動機：{為什麼要找——讓它能判斷邊界案例，例如「我要改它的回傳格式，需要完整呼叫面」}。
範圍：{目錄 / 檔案類型}；不用讀 {排除範圍，例如 tests/、docs/}。
回報格式：每筆 = 檔:行 + 一句話說明該處在做什麼；按 {分類方式} 分組；
找不到也要明說「掃過 X、Y、Z 沒有」，不要沉默略過。
不要：貼大段程式碼原文（每筆最多 3 行摘錄）。
```

## T2 實作（general-purpose；難度低 sonnet、跨模組/安全相關 opus）

```
目標：{要實作的行為，一句話}。
動機：{業務理由 / 上游決策，例如「e2e 發現 X 狀態不同步」}。
規格：
- {輸入 → 輸出 / 行為變化，逐條}
- 既有慣例：參考 {檔:行 的既有範例}，風格對齊它。
範圍圍欄：只動 {檔案清單}；不改測試斷言、不動 {禁區}；不寫營運 DB；
不 commit（commit 由主 session 統一做）。
驗收條件（做完自己先過一遍）：
- {對應測試} 綠，且新行為有新測試蓋住
- 跑 {測試指令，預設 .venv/bin/python3 -m pytest mcp-servers/business-db/tests/ -q}，輸出落檔到 {scratchpad 路徑}
回報格式：改了哪些檔（檔:行）+ 每個檔一句話 + 測試結果數字 + 你不確定的點列出來。
長輸出（diff / log）落檔傳路徑，不要貼全文。
```

## T3 重構（general-purpose，sonnet；模式必須由主 session 先解出）

```
目標：把 {既有模式 A} 改成 {模式 B}，行為不變。
動機：{為什麼重構}。
完整範例（我已改好一處，照這個模式套用）：
{貼出一處完整的 before/after diff}
套用清單：{檔:行 列表——主 session 先用 T1 搜齊，不要讓重構 agent 自己找}。
邊界清單：{已知的特殊 case 與處理方式}；碰到清單外的變體 → 跳過並回報，不要自行發明。
驗收條件：全量回歸綠（行為不變的定義就是測試不變且綠）；被跳過的變體逐筆列出。
回報格式：套用成功 N 處（檔:行）/ 跳過 M 處（檔:行 + 原因）+ 測試數字。
```

## T4 研究（general-purpose，sonnet）

```
目標：回答這些問題：{問題清單，逐條編號——問題越具體、答案越可用}。
動機：{要做什麼決策，讓它知道哪類資訊是雜訊}。
來源要求：{官方文件 / 原始碼 / 特定網站}；每個結論附來源（URL 或 檔:行）；
查不到就說查不到，不要用訓練記憶補——標明「這是我的既有知識、未經查證」也可以，但要標。
回報格式：按問題編號逐條回答；每條 = 結論一句話 + 證據 + 信心（查證過 / 推測）。
長文摘錄落檔傳路徑。
```

## T5 審查（兩路並行：fresh agent + codex）

**T5a — fresh-context agent read-back（檔案 / 文件類）**
```
目標：驗收這些檔案：{路徑清單}。你沒有做這些檔的脈絡——這是刻意的，請獨立判斷。
逐項回答：
1. 每個檔案存在且非空？（ls 實查）
2. {驗收問題清單——來自派工時寫下的驗收條件，逐條}
3. 檔案之間有沒有互相矛盾的規則？有的話引兩邊原文。
4. 檔內提到的路徑 / 工具名 / 指令，抽查 {N} 個，實際驗證存在（ls / grep / --help）。
回報格式：每項 PASS / FAIL + 證據；FAIL 附最小修法建議。不要客套。
```

**T5b — codex 對抗審（程式類；呼叫方式見 `10-model-dispatch.md` §4）**
```
（prompt 檔開頭給脈絡：branch、改動範圍、怎麼跑測試）
請對抗式審查 {git diff 範圍 / 檔案清單}：
- 找 correctness bug、安全洞（floor/gate/actor/去識別化）、假綠測試、regression。
- 對每個 finding：嚴重度 + 檔:行 + 具體失敗場景（什麼輸入/狀態會炸）+ 最小修法。
- 全部沒問題就明講「無 actionable finding」。不要客套、不要複述我的說明。
```
收斂標準：codex 連續一輪零 actionable finding = READY。它的 finding 也要先用測試證實再修（false positive 有實績）。

## 通用附註

- **升級時的 payload**：附完整失敗軌跡（前幾輪的 prompt、輸出、你判斷錯在哪），不是只丟原始任務。
- **平行派工**：互不依賴的 T1/T4 可以多隻同時發；有依賴就串行，別讓兩隻 agent 同時改同一批檔。
- **派工後不要自己也做一遍**：等結果。結果可疑就走 T5 驗收，驗收與宣稱衝突時信驗收。
